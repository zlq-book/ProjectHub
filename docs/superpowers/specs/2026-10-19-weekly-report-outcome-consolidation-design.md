# ProjectHub：AI 周报成果按主题归纳设计

日期：2026-10-19。状态：已实施并通过前端、构建与 Rust 测试。相关模块：`src-tauri/src/services/weekly_report/`、`src/components/weekly-report/`。

## 1. 问题与目标

用户反馈：AI 智能周报的“候选工作成果”基本是一条 Git 提交生成一条成果，正文接近提交说明的转述，没有形成适合周报的业务归纳。

目标：把所选提交、开发日志和手选 Diff 按功能、模块、需求或问题修复归纳为 **全局合计 4–8 条**候选成果，用户仍从中勾选最多 4 条导出。原有“人工编辑、按入选顺序导出、来源可追溯”的约束不变。

## 2. 已确认决策

| 决策 | 结果 |
| --- | --- |
| 归纳粒度 | 按功能主题合并，不按提交逐条生成 |
| 候选数量 | 全局 4–8 条；材料主题不足 4 个时按实际主题 1–3 条，不强行凑数 |
| 硬上限 | 服务端拒绝超过 10 条候选 |
| 跨项目合并 | 同一业务事项允许合并，项目名用“、”连接 |
| 请求协议 | 不变：仍为一次预览、一次确认、一次请求 |
| 数据与版本 | 不改数据库 schema、备份格式和已保存版本；旧草稿继续可读 |
| 提示词之外 | 不引入两阶段 AI 调用，不新增手动合并工具 |

## 3. 生成提示词

`generation.rs` 的 `SYSTEM` 从“给出全部候选”改为明确归纳任务：

- 目标：全局 4–8 条业务成果；材料主题不足 4 个时 1–3 条；最多 10 条。
- 合并：同一功能、模块、需求或问题修复的多条提交合并为一条；跨项目同一事项可合并；相近主题不得拆成多条。
- 写法：每条 1–2 句，说明完成的工作和形成的业务能力；以项目名开头，多个项目用“、”；不复述提交标题，不罗列文件名、提交号或“提交了”之类过程。
- 证据：每条成果引用能证明它的真实 `sourceIds` 和对应 `projectIds`；合并后的成果引用被合并的相关提交；不得引用未提供材料。
- 真实性：不虚构完成率、上线、验收、测试结果或业务收益；困难、计划、感悟仍只润色人工要点，空要点返回空。

JSON 结构、长度限制、`max_tokens` 与现有 `thinking` 兼容参数保持不变。

## 4. 服务端校验

在 `generation::parse()` 中新增：

- 候选超过 10 条时返回错误，提示“模型返回 N 条候选，未按功能主题合并，请重新生成或缩小材料范围”，不创建版本。
- 原有校验保留：未知来源、空来源、伪造项目、重复 ID、空正文、未填写要点被补写、单条长度与模板容量。
- 不强制要求引用每一条所选材料；覆盖情况由前端展示，避免输出 token 随材料数量无限膨胀。

`ReportContent::validate()` 仍允许人工新增到 100 条，不把 AI 的 10 条上限强加给人工编辑。

## 5. 编辑页展示

`OutcomeEditor`：

- 标题下增加摘要：`AI 已按功能主题归纳为 N 条候选，覆盖 M 条材料。`（N 为 AI 草稿条数，M 为这些草稿引用到的不同 `sourceIds` 数；无 AI 草稿时不显示）。
- 每条 AI 草稿标题后显示“覆盖 N 条材料”。
- “查看依据（N）”改为“查看依据（N 条材料）”，展开内容不变。

`WeeklyReportWorkspace` 准备页：

- 在材料提示附近增加一句：生成时按功能主题归纳为 4–8 条候选成果，不会逐条罗列提交。

## 7. 不包含

- 两阶段聚类请求或本地按目录预分组。
- 手动“合并选中成果”的批量操作。

- 强制每条材料都被引用。
